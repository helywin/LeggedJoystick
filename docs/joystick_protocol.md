# UniRC 10 Pro 摇杆/遥控通道数据协议

> 来源：《UniRC 10 Pro V1.0.md》第 6 章 SDK 通讯协议  
> 整理范围：协议帧格式、摇杆/通道数据命令（CMD_ID = 0x42）、通道映射定义、CRC16 校验及通讯接口。

---

## 1. 协议帧格式

所有 SDK 数据包采用统一帧结构，**小端模式（Little-Endian）**。

| 字段      | 索引 | 字节长度 | 内容说明 |
|----------|------|---------|---------|
| STX      | 0    | 2       | 起始标志，固定为 `0x55 0x66` |
| CTRL     | 2    | 1       | bit0：`need_ack`（是否需要 ACK）<br>bit1：`ack_pack`（是否为 ACK 包）<br>bit2~7：预留 |
| Data_len | 3    | 2       | 数据域字节长度，低字节在前 |
| SEQ      | 5    | 2       | 帧序列号，范围 `0 ~ 65535`，低字节在前 |
| CMD_ID   | 7    | 1       | 命令 ID |
| DATA     | 8    | Data_len| 数据内容 |
| CRC16    | -    | 2       | 整个数据包的 CRC16 校验，低字节在前 |

### 1.1 控制字节（CTRL）

| 位   | 名称       | 说明 |
|-----|-----------|------|
| 0   | need_ack  | `1`：需要对方回复 ACK；`0`：不需要 |
| 1   | ack_pack  | `1`：当前包为 ACK 包；`0`：不是 |
| 2~7 | reserved | 预留 |

## 2. 摇杆/遥控通道数据（CMD_ID = 0x42）

该命令用于**订阅/接收遥控器 16 路通讯通道的实时数据**，摇杆、拨轮、旋钮、开关、按键等物理量最终都会映射到这 16 个通道中。

### 2.1 发送请求（开启/关闭通道数据输出）

向遥控器发送以下数据，设置通道数据的输出频率。需要**连续发送三次**以确保设置生效。

| 序号 | 数据类型 | 数据名 | 数据说明 |
|-----|---------|--------|---------|
| 1   | uint8_t | freq   | 输出频率 |

#### freq 取值

| 值   | 含义     |
|-----|---------|
| 0   | 关闭发送 |
| 1   | 2 Hz    |
| 2   | 4 Hz    |
| 3   | 5 Hz    |
| 4   | 10 Hz   |
| 5   | 20 Hz   |
| 6   | 50 Hz   |
| 7   | 100 Hz  |

#### 发送示例

| 功能       | HEX 帧 |
|-----------|--------|
| 开启 4 Hz 输出 | `55 66 01 01 00 00 00 42 02 B5 C0` |
| 关闭输出    | `55 66 01 01 00 00 00 42 00 F7 E0` |

> 帧解析（以 4Hz 为例）：
> - `55 66`：帧头
> - `01`：需要 ACK
> - `01 00`：数据长度 1
> - `00 00`：序列号 0
> - `42`：命令 ID
> - `02`：4 Hz
> - `B5 C0`：CRC16

### 2.2 回复数据（ACK）

遥控器按设定频率持续返回 16 个通道值，每个通道占 **2 字节（int16_t）**，默认数值范围为 **1050 ~ 1950**，中位为 **1500**。

| 序号  | 数据类型 | 数据名 | 数据说明 |
|------|---------|--------|---------|
| 1    | int16_t | CH1    | 通道 1 数值 |
| 2    | int16_t | CH2    | 通道 2 数值 |
| ...  | int16_t | ...    | ... |
| 16   | int16_t | CH16   | 通道 16 数值 |

#### 回复示例（2 Hz）

```text
55 66 00 20 00 99 00 42
DC 05 DC 00 DC 05 DC 05 DC 05 DC 05 DC 05 DC 05
DC 05 DC 05 1A 04 DC 05 DC 05 1A 04 1A 04 1A 04
FF 88
```

- `55 66 00 20 00 99 00 42`：帧头 + 无需 ACK + 数据长度 32 + SEQ + CMD_ID
- 后面 32 字节为 CH1 ~ CH16（每个通道 2 字节，小端）
- `FF 88`：CRC16

## 4. CRC16 校验代码

多项式：`G(X) = X^16 + X^12 + X^5 + 1`

```c
const uint16_t crc16_tab[256];

uint16_t CRC16_cal(uint8_t *ptr, uint32_t len, uint16_t crc_init)
{
    uint16_t crc, oldcrc16;
    uint8_t  temp;

    crc = crc_init;
    while (len-- != 0)
    {
        temp = (crc >> 8) & 0xff;
        oldcrc16 = crc16_tab[*ptr ^ temp];
        crc = (crc << 8) ^ oldcrc16;
        ptr++;
    }
    return crc;
}

uint8_t crc_check_16bites(uint8_t* pbuf, uint32_t len, uint32_t* p_result)
{
    uint16_t crc_result = 0;
    crc_result = CRC16_cal(pbuf, len, 0);
    *p_result = crc_result;
    return 2;
}
```

## 5. 通讯接口

UniRC 10 Pro 提供多种接口供外部设备接收 SDK 数据（含 0x42 通道数据）。

| 接口类型 | 地址/设备节点 | 波特率/端口 |
|---------|--------------|------------|
| 串口 1  | `/dev/ttyHS3` | 115200     |
| 串口 2  | `/dev/ttyHS0` | 115200     |
| 蓝牙    | -            | -          |
| Type-C  | USB 虚拟串口  | -          |
| UDP     | 服务器 IP：`192.168.144.20` | `19856` |

> 注意：客户端端口号请勿使用 `19856`，以免与遥控器服务端端口冲突。

## 6. 快速参考

### 6.1 接收摇杆数据的最小流程

1. 选择通讯接口（推荐 UDP `192.168.144.20:19856` 或串口 `/dev/ttyHS3`）。
2. 发送开启命令：`55 66 01 01 00 00 00 42 02 B5 C0`（连续三次，4 Hz）。
3. 接收 ACK：`55 66 00 20 00 99 00 42 <32 bytes CH1~CH16> <CRC16>`。
4. 按小端解析每个通道的 `int16_t` 数值，默认范围 1050~1950。
5. 如需停止，发送关闭命令：`55 66 01 01 00 00 00 42 00 F7 E0`（连续三次）。

### 6.2 数值范围说明

| 参数 | 默认值 | 说明 |
|-----|--------|------|
| 通道最小值 | 1050 | 对应摇杆/开关的低位 |
| 通道中位值 | 1500 | 摇杆中立位置 |
| 通道最大值 | 1950 | 对应摇杆/开关的高位 |
| 行程量中位偏移范围 | ±500 | 可通过 APP 调整中立点 |

## 7. App 侧接入边界

本文档描述的是 UniRC 10 Pro 原始 SDK 通道帧，不是新遥控 App 对机器狗发送的最终控制协议。新 App 仍以 `legged_driver` 的 `COMMAND_CODE_MOVE`、`COMMAND_CODE_SET_SPEED_LEVEL` 和动作命令作为机器人控制出口。

### 接收职责

| 项 | 决策 |
| --- | --- |
| App 角色 | 接收摇杆/通道数据，并转换为内部输入状态 |
| 命令出口 | 只有 `legged_driver` 协议发送层可以对机器人发命令 |
| 广播状态 | 第一版不实现；后续如需多 App 共用摇杆数据，可作为单采集者分发方案再评估 |
| 核心约束 | 第一版只接收 UniRC UDP；未来即使接入广播，也必须走同一套解析、归一化、输入状态更新和零速度保护 |

### 输入管线

| 阶段 | 说明 |
| --- | --- |
| 原始接收 | 第一版读取 UniRC UDP 通道帧 |
| 帧校验 | 校验 STX、Data_len、CMD_ID、CRC16 |
| 通道提取 | 解析 CH1 到 CH16，保留原始 int16 值 |
| 归一化 | 使用 center/min/max/dead_zone/invert 配置转换成运动轴 |
| 输入状态 | 当前版本只接受外部摇杆链路；如后续接入 Android 分发数据，也必须转换为同一份通道状态 |
| 控制输出 | 由移动命令循环读取最新输入状态，按 20Hz 到 30Hz 发送 `COMMAND_CODE_MOVE` |

### 广播作为未来可选方案

第一版不实现 Android 广播输入。如果后续需要其他 App 也使用同一份摇杆数据，可以增加 Android 广播接收适配器。广播只负责传输原始或半解析通道数据，不直接表达机器人动作命令。

| 要求 | 说明 |
| --- | --- |
| 安全边界 | 使用显式 action、固定 package、签名级权限或同签名应用 |
| 数据内容 | 至少包含时间戳、序列号、CH1 到 CH16、数据源标识 |
| 时效性 | 数据超时后输入层必须置零，不沿用旧摇杆值 |
| 发送频率 | 可高于机器人移动命令频率，App 只取最新帧 |
| 调试 | UI 可显示最近一帧原始通道值、归一化轴值和输入源状态 |

广播方案不改变控制安全策略：未接管控制、连接断开、页面后台、输入超时或 `driver` 停止保护状态下，都必须拦截运动输出或停止速度输出。

### 多 App 共用结论

当前本机实测表明：两个进程同时绑定同一个 UDP 端口并接收单播包时，数据不会被复制给两个进程；20 个测试包全部进入后绑定的接收者，另一个接收者收到 0 个。因此不能依赖“UDP 同端口复用”让多个 App 同时收到同一份摇杆流。

当前设备 `Standard-10inch_A2` 已确认本机 UDP 入口 `127.0.0.1:19856` 来自 `com.siyi.udpservice`，该服务桥接 `/dev/ttyHS3`。新 App 走本机 UDP 桥时，另一个进程直接读取 `/dev/ttyHS3` 会竞争同一条串口字节流：串口直读基线 3 秒可解析 37 个完整 `0x42` 帧，并发时降到 6 个完整帧，App 端同时出现输入超时和恢复抖动。因此不能按“新 App 用本机 UDP、其他 App 直接读串口”分配独立输入接口。

后续仍需要确认：

| 验证项 | 结论依据 |
| --- | --- |
| 不同本地 UDP 端口是否都能订阅 | 已验证两个端口都能收到部分 0x42 通道帧，但本机 UDP 桥更接近最近客户端地址模型，不适合作为多个 App 稳定共享方案 |
| `freq = 0` 影响范围 | 串口直测未发现会停止 `/dev/ttyHS3` 通道输出；第一版仍不主动发送关闭频率帧 |

如果多个 App 必须共用摇杆数据，推荐方案是单独做一个摇杆采集者，由它独占本机 UDP 桥或串口，再在 Android 侧分发给其他 App。分发方式优先考虑绑定服务；如果必须跨 App 广播，则使用显式 action、固定 package、签名级权限或同签名应用。
