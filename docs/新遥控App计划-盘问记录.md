## 会话状态

- 状态：进行中
- 当前重点：新 App 使用本机 UniRC UDP 桥作为正式输入；已确认本机 UDP 桥和直接读取 `/dev/ttyHS3` 会竞争，不能作为两个 App 的独立输入通道。

## 关键结论

- 串口和 UDP 独立性采用严格判定：同时稳定收到通道数据，并验证启动、停止、重连、改频互不影响；当前设备实测未通过该判定。
- 当前使用方式：新遥控 App 使用本机 UDP 桥 `127.0.0.1:19856`；其他 App 不能再直接读取 `/dev/ttyHS3` 作为并行摇杆输入。
- 通道输出配置归属：新遥控 App 通过本机 UDP 桥发送 UniRC `CMD_ID = 0x42` 的开启和频率配置；多 App 共用时必须改为单采集者分发。
- 外部 App 违规配置时，新 App 采用检测并自恢复：UDP 帧率异常或中断时重新发送开启/频率配置，持续失败则进入摇杆失效和零速度保护。
- 严格验证必须覆盖普通 Android App 进程读取串口，不能只用 ADB shell 结果代表产品可用。
- App 进程串口探测入口放在新 App 调试页，作为内部调试功能，不做单独示例工程。
- 新 App 正式遥控输入只使用 UDP；串口仅用于内部调试验证和现场诊断，不作为 UDP 失败时的备用控制输入。
- UDP 摇杆通道默认请求 50 Hz；低于目标 60% 持续 1 秒，或超过 300 ms 没有新帧，判定链路异常并触发自恢复。
- 外部摇杆第一版只映射移动轴，不映射速度档，不解析 L1/L2/L3；低速、中速、高速只由 UI 左侧速度选择器设置。
- 外部 UDP 摇杆只解析 `CH3` 前后、`CH4` 左右平移、`CH1` 转向；其他通道仅在调试页显示原始值，不参与速度、动作、模式或灯光控制。
- `COMMAND_CODE_MOVE` 默认按 25 Hz 连续发送。
- 移动轴归一化默认死区为 0.06。
- UniRC 摇杆通道固定按 `1050 -> -1.0`、`1500 -> 0`、`1950 -> 1.0` 归一化，超出范围 clamp 到 `[-1, 1]`。
- 三轴默认方向按操作者直觉保存为内部意图：左手前推为前进正值，左手右推为右平移正值，右手右推为右转正值；发送到 `legged_driver` 时必须按 SDK 符号转换，`MoveCommandParams.left_right` 正数是左平移、`yaw` 正数是左旋转，因此右平移和右转默认要取负值。
- UI 速度档默认低速；接管成功后先发送低速，随后以 `RobotStateMessage.speed_level` 回传校正。
- 顶部运动模式默认显示普通模式占位并标记同步中；收到 `RobotStateMessage.sport_mode` 后按实际状态显示。接管成功后如机器人模式未知，则先发送普通模式。
- 离散命令不自动重试：接管、释放、速度、模式、动作、灯光失败或 rejected 时只提示用户，不自动重发；移动命令发送失败只记录并由下一周期或连接状态机处理。
- 离散命令 pending 超时：普通命令默认 3 秒，接管/释放默认 5 秒；动作命令 accepted 后等待 `motion_status` 回传时显示执行中，不按 3 秒判失败。
- 电量状态 overlay 保留双电池布局；未知电池显示 `--` 和灰色电池图标，单电池有效时另一块显示 `--`。
- 第一版需要工程 mock 模式，只放工程调试入口，用于 UI 验证、截图和回归测试，不发送真实 ZMQ/UDP。
- 移动控制意图：左手摇杆控制前进/后退和左右平移，右手摇杆控制转向。
- 移动轴第一版默认按 `CH3/J3 = 左手前后`、`CH4/J4 = 左手左右平移`、`CH1/J1 = 右手转向` 推进，调试页必须显示 `CH1` 到 `CH4` 原始值并支持低速确认轴向。
- UDP+串口独立性验证已确认失败；`legged_driver` 协议闭环、主屏 UI 和外部 UDP 摇杆输入继续推进，多 App 共用后续按单采集者分发设计。
- 第一阶段交付主控基础版：GenisDog 风格主屏、外部 UDP 摇杆输入、`legged_driver` 连接/心跳/状态订阅、移动命令、速度三档、零速度保护和调试页；当前不做触屏虚拟摇杆。
- 第一阶段视频不作为硬门槛；主屏按视频背景叠层设计，但可以先用占位背景或可配置视频地址空状态完成控制 overlay。
- 未拿到 `legged_driver` 控制权，或控制权状态未知时，禁止发送 `COMMAND_CODE_MOVE`；控制权丢失、未知或接管失败时发送零速度并停止移动循环。
- 主屏功能按反编译 App 已有功能范围设计，不单独增加急停按钮；停止保护由 `driver` 侧看门狗承担，App 侧负责在释放、后台、断连、失去控制权时停止移动输出。
- 接口验证结果：`legged_driver` 已覆盖站立、匍匐、卧倒、扭一扭、爬高墙/爬高台、过窄墙、锁定、速度三档、运动模式、灯光、头部控制、高低姿态、接管/释放和移动控制；`过挡鼠板` 在官方 SDK 中未找到同名或同语义接口；`巡航模式` 不在 `SportMode` 枚举中。
- `过挡鼠板` 不做，不显示，也不映射到 `ReverseHeadTail`。
- `巡航模式` 不做，不显示；官方 SDK 只支持通用、原地、登阶三种模式。
- 普通设置只暴露机器狗 IP、ZMQ 端口和视频地址；摇杆通道映射、轴反向、UDP 频率、串口探测和原始通道值只放工程调试页。
- 工程调试参数默认不自动持久化；只保存连接类配置和用户明确确认“保存为默认”的通道/输入参数。
- 控制权释放策略：用户主动退出主控页或点击释放时发送 `RELEASE_CONTROL`；后台只停止速度输出并暂停控制；ZMQ 断开后控制权标记为未知，重连后必须重新确认或重新接管。
- 视频失败、卡顿或解码异常不阻断遥控；视频层只显示断流/重连状态，控制链路独立工作。
- 当前没有触屏虚拟摇杆；屏幕只负责按钮、模式、速度、状态和调试入口，正式移动输入来自外部 UDP 摇杆。
- 外部 UDP 摇杆不可用、超时或持续自恢复失败时禁用移动输出，但保留连接、接管/释放、模式、速度、状态查看、调试页和非移动类动作按钮。
- 运动相关命令必须要求控制权：站立、卧倒、匍匐、爬高墙、扭一扭、过窄墙、锁定、运动模式、速度等级都要在控制权属于本 App 时发送；灯光和状态查看不要求控制权。
- 速度和模式命令显示发送中，并在 `COMMAND_RESULT accepted` 后乐观更新，最终以 `RobotStateMessage` 回传校正；动作按钮只显示发送中/成功/失败，最终状态以 `motion_status` 为准。
- 第一版 UI 只适配当前 10 寸横屏设备，后续其他设备另做适配。
- App 后台保持 ZMQ 和 UniRC UDP 长连接，但停止移动输出和动作发送。
- 后台长连接使用前台服务和常驻通知；进入主控页并连接机器狗时启动，退出主控页或释放控制后停止。
- 调试页保留轻量环形日志，记录最近 5 到 10 分钟的连接状态、控制权变化、命令发送/结果、UDP 帧率/超时、自恢复和最近通道值摘要；默认不记录高频完整原始帧。
- 开发和内部联调可以临时使用 GenisDog 抓取素材；正式发布前替换为自有或已授权素材。可以用 imagegen 生成部分素材，但最终放入项目的图标必须是经工具处理后的透明背景 PNG。
- App 连接到 `legged_driver` 后不自动接管；必须用户手动点击接管才发送 `COMMAND_CODE_TAKE_CONTROL`。
- 进入主控页并启动前台服务后订阅 UniRC UDP 摇杆，不等用户接管；未接管前只显示摇杆状态，移动命令仍被拦截。
- `freq = 0` 串口直测未发现会停止 `/dev/ttyHS3` 通道输出；第一版正常退出主控页或停止前台服务时仍不默认发送 UniRC `freq = 0`，只停止本 App 移动输出和输入消费。本机 UDP 桥和直接串口读取已确认竞争，不再把关闭 UDP 输出作为并行串口方案的前提。
- 新 App 继续使用当前仓库单 `app` 模块工程壳，但按新分层重建主实现；旧 UI、旧协议、旧虚拟摇杆和厂商相关入口不作为新实现依赖。
- 构建栈升级到当前稳定线：Gradle 9.6.0、Android Gradle Plugin 9.2.1、Kotlin 2.4.0、Compose BOM 2026.06.00、Wire 6.4.0，并把 `compileSdk` 升到 37；依赖升级不采用 alpha、beta、RC、EAP、snapshot 或 nightly。
- ADB 当前设备：`Standard-10inch_A2`，Android 13，存在 `/dev/ttyHS0` 到 `/dev/ttyHS3`，节点权限位均为可读写；普通 App 是否可打开仍需用 App 进程实测。

## 轮次记录

### 第 1 问：串口和 UDP 独立性的判定标准

**问题：** 我们要用什么标准判定“串口和 UDP 是两个独立通道”，从而允许新 App 用 UDP，其他 App 用串口？

**推荐答案：** 在同一台遥控器、同一时间窗口内，同时运行 UDP 订阅和串口读取；两边都能连续收到 `CMD_ID = 0x42` 的 CH1 到 CH16，并且其中一路启动、停止、重连不会让另一路中断或改频，才算独立。

**用户回答：** 选择 1，采用严格判定。

**当前判断：** 串口和 UDP 的独立性不能只看“同时收到数据”，还要验证启动、停止、重连和频率配置是否互相影响。后续测试必须记录两路的包频率、连续性和异常中断。

**下一步：** 确认通道输出配置命令的归属，避免两个 App 分别通过不同通道发送开启、关闭或改频命令导致互相干扰。

### 第 2 问：通道输出配置命令归属

**问题：** 在验证和最终产品里，谁负责发送 UniRC `CMD_ID = 0x42` 的开启、关闭和频率配置命令？

**推荐答案：** 由新 App 通过 UDP 统一发送开启和频率配置，串口侧其他 App 只读通道数据，不发送开启、关闭或改频命令；关闭输出只在明确退出采集或调试结束时手动触发。

**用户回答：** 选择 1，并明确新 App 使用 UDP，其他 App 使用串口。

**当前判断：** 计划按“UDP 负责配置和新 App 输入，串口只作为其他 App 的只读输入通道”推进。后续验证必须防止串口侧发送关闭或改频命令，否则会污染独立性测试。

**下一步：** 确认其他 App 是否可控，以及是否能强制串口侧只读。

### 第 3 问：其他 App 是否可控

**问题：** 使用串口的“其他 App”是否由你控制，能不能要求它只读取 `/dev/ttyHS*` 通道帧，不发送 `CMD_ID = 0x42` 的开启、关闭或改频命令？

**推荐答案：** 其他 App 由你控制或可修改，并约束为只读串口；新 App 独占 UDP 配置权。

**用户回答：** 其他 App 不能控制，但会要求他们不要发送开启、关闭或改频命令。

**当前判断：** “串口侧只读”只能作为外部集成契约，不能作为新 App 可强制保证的技术前提。计划需要明确：如果其他 App 违反约束，新 App 能检测到什么、提示什么，以及是否进入回退方案。

**下一步：** 确认新 App 对外部 App 违规配置的容错目标。

### 第 4 问：外部 App 违规配置时的容错目标

**问题：** 如果其他 App 虽然被要求只读串口，但实际仍通过串口发送关闭、改频或重新开启 `CMD_ID = 0x42`，新 App 需要做到什么程度的防护？

**推荐答案：** 新 App 不阻止外部 App 违规配置，但要检测 UDP 通道数据频率异常或中断，自动重新发送 UDP 开启/频率配置，并在调试面板提示“外部输入链路可能被改频或关闭”；若连续恢复失败，则进入外部摇杆失效并零速度保护。

**用户回答：** 选择 1，采用检测并自恢复。

**当前判断：** 新 App 需要把 UDP 摇杆链路当成可能被外部改频或关闭的输入源处理。发现帧率异常、中断或恢复失败时，先尝试重新发送 UDP 开启/频率配置；持续失败时进入摇杆失效和零速度保护，并在调试面板提示外部链路异常。

**下一步：** 确认真机验证是否必须覆盖普通 Android App 进程的串口访问能力。

### 第 5 问：串口验证必须覆盖 App 进程吗

**问题：** 严格验证“新 App 用 UDP，其他 App 用串口”时，是否必须验证普通 Android App 进程能打开并读取 `/dev/ttyHS*`，而不仅仅是 ADB shell 能读取？

**推荐答案：** 必须覆盖普通 Android App 进程。先用 ADB shell 找到真实输出通道，再做一个最小 Android 探测入口或集成到调试页，用 App UID 打开串口并读取 CH1 到 CH16。

**用户回答：** 选择 1，必须覆盖 App 进程。

**当前判断：** ADB shell 只能作为初筛。产品计划里必须加入 App UID 下的串口读取验证，至少确认目标设备上普通 App 能打开对应 `/dev/ttyHS*`，并能解析 `CMD_ID = 0x42` 的 CH1 到 CH16。

**下一步：** 决定 App 进程串口探测入口的实现位置。

### 第 6 问：App 进程串口探测入口放在哪里

**问题：** 为了验证普通 App 进程能读串口，探测入口应该放在新遥控 App 的调试页里，还是做一个单独的内部探测 APK？

**推荐答案：** 放在新遥控 App 的调试页里，但作为内部调试功能隐藏，不做示例工程。这样同一个 App UID、同一套权限和后续产品环境一致，也能复用通道解析和调试面板。

**用户回答：** 选择 1，放进新 App 调试页。

**当前判断：** 串口探测不作为示例代码独立存在，而是新 App 内部调试能力。它必须复用正式输入层的帧解析、CRC 校验和通道显示，避免探测逻辑和产品逻辑分叉。

**下一步：** 确认新 App 是否只把串口用于探测，还是也作为 UDP 失败时的备用输入来源。

### 第 7 问：新 App 是否保留串口备用输入

**问题：** 新 App 的正式遥控输入是否只使用 UDP，串口仅用于调试验证；还是在 UDP 失败时允许新 App 切到串口作为备用输入？

**推荐答案：** 正式遥控只使用 UDP，串口仅用于内部调试验证和现场诊断。因为你的目标是“新 App 用 UDP，其他 App 用串口”，如果新 App 也把串口作为备用输入，会和其他 App 的串口使用边界冲突。

**用户回答：** 选择 1，正式遥控只用 UDP，串口仅调试。

**当前判断：** 新 App 不把串口纳入正式输入仲裁。串口调试页只用于证明其他 App 可走串口和诊断链路状态，不参与移动命令输出。

**下一步：** 确认 UDP 摇杆输出频率目标和异常阈值。

### 第 8 问：UDP 摇杆输出频率

**问题：** 新 App 通过 UDP 订阅 UniRC `CMD_ID = 0x42` 通道数据时，默认应请求多少输出频率，以及低于什么程度算异常需要自恢复？

**推荐答案：** 默认请求 50 Hz；运行时低于目标的 60% 持续 1 秒，或超过 300 ms 没有新帧，就判定 UDP 链路异常并重新发送开启/频率配置。50 Hz 能给控制输入留足刷新率，同时数据量很小。

**用户回答：** 选择 1，使用 50 Hz + 异常自恢复。

**当前判断：** 输入层需要持续统计 UDP 通道帧率和最后收帧时间，并把实际帧率、超时状态、自恢复次数显示到调试面板。自恢复不能绕过零速度保护：恢复期间不沿用旧摇杆值。

**下一步：** 确认外部摇杆通道是否只管移动，还是也参与动作触发。

### 第 9 问：外部摇杆通道映射范围

**问题：** UniRC 外部摇杆通道在新 App 里只用于移动轴输入，还是也允许映射三档速度、运动模式、站立/卧倒/急停等按钮动作？

**推荐答案：** 第一版只把外部摇杆用于移动轴和速度倍率，不直接触发高风险动作；站立、卧倒、急停、运动模式等仍由屏幕 UI 明确触发。这样能降低通道映射错误导致误动作的风险。

**用户回答：** 原先选择 1，并提出 L1/L2/L3 映射速度档；后续在第 40 问改为速度档只由 UI 设置，不做 L1/L2/L3。

**当前判断：** 外部摇杆不直接触发动作命令，也不影响速度档。输入层只从外部摇杆解析移动轴；速度档由 UI 左侧速度选择器设置。

**下一步：** L1/L2/L3 相关问题作废。
